## 구현 현황 (2026-06-01, 프로토타입)

기획에 그치지 않고 **MVP 척추를 CPU에서 실제로 구현·측정**했다. 코드는 `reviewlens/` 참고.

- **동작**: 리뷰 → 속성 감성(ABSA) → 감성 저장소(SQLite) → 설명가능 추천 + 근거기반 챗봇 + 웹 UI(FastAPI). 전부 CPU.
- **사용 모델**: ABSA = `matthewburke/korean_sentiment`(부트스트랩) / **Ollama `qwen2.5:3b`**(LLM ABSA·챗봇). 추천 = **implicit ALS + 감성 블렌딩**. 임베딩·FAISS·파인튜닝은 다음 단계.
- **실측 ABSA 성능** (gold 39 라벨):

  | 분석기 | 정밀도 | 재현율 | F1 |
  |---|---|---|---|
  | 규칙 + KoELECTRA | 0.86 | 0.82 | 0.84 |
  | LLM (qwen2.5:3b) | 1.00 | 0.74 | 0.85 |

  → 정밀도-재현율 트레이드오프, F1 거의 동률. 둘 다 천장 → **하이브리드/파인튜닝이 다음**. (gold 소규모·단일 라벨러라 방향성 지표)
- **실측 추천 성능** (`recommender.py`, 합성 상호작용 시뮬레이터, 시간 기반 분할, Recall@10/NDCG@10):

  | 유저 그룹 | 방법 | Recall@10 | NDCG@10 |
  |---|---|---|---|
  | 따뜻한(n=143) | popularity | 0.185 | 0.191 |
  | | implicit ALS | 0.201 | 0.224 |
  | | ALS + 감성 블렌딩 | **0.310** | **0.331** |
  | 콜드스타트(n=47) | popularity | 0.156 | 0.211 |
  | | 감성 fallback | **0.260** | **0.352** |

  → 순수 CF는 인기도를 소폭 상회, **감성 블렌딩이 크게 향상**(하이브리드 효과). 콜드스타트에선 감성 fallback이 인기도를 명확히 상회.
- **LightFM → implicit 교체**: 당초 LightFM(하이브리드)을 계획했으나 유지보수 중단으로 Python 3.12 + 최신 setuptools/numpy 2.x에서 **빌드 불가**. 유지보수되는 `implicit`(ALS, CPU 네이티브)로 CF 백본을 옮기고, LightFM의 *아이템 사이드피처(감성)* 역할은 **감성 스코어러 블렌딩**으로 대체. §5.2·§8의 LightFM 표기는 이 대체를 전제로 읽을 것.
- **현재 vs 계획 차이(의도된 단순화)**: 추천 상호작용은 실데이터 부재로 **문서화된 합성 시뮬레이터**(로더만 바꾸면 Amazon-Reviews-2023로 교체), 챗봇 검색은 임베딩 대신 **키워드**(리뷰 18개 규모, phase 2에서 FAISS로 교체).

## 2. 문제 정의 및 핵심 과제

온라인 상품과 서비스의 리뷰 수는 계속 증가하지만, 리뷰가 많아질수록 사용자는 핵심 판단 근거를 찾기 어려워지고 운영자는 개선 포인트를 놓치기 쉽습니다. 기존 리뷰 시스템은 대체로 별점 평균이나 전체 긍정/부정 요약에 머무르기 때문에 "무엇이 좋고 나쁜지"를 구체적으로 설명하지 못합니다.

| 문제 | 상세 내용 | ReviewLens 해결 방향 |
|---|---|---|
| 정보 과부하 | 수천 개 리뷰를 직접 읽어야 해 구매 판단과 운영 분석이 느림 | 속성별 감성 분석과 요약 KPI 제공 |
| 감성 단위가 큼 | 전체 긍정/부정만으로는 가격·품질·배송·포장 등 세부 원인 파악 불가 | ABSA로 속성별 긍정/부정 분리 |
| 추천 근거 부족 | 추천 결과는 나오지만 왜 추천됐는지 설명이 약해 신뢰도 낮음 | 추천 결과에 리뷰 근거와 속성 점수 연결 |

**핵심 과제**: 리뷰를 "읽는 데이터"에서 "질문하고, 비교하고, 추천받는 데이터"로 전환하는 것.

## 3. 서비스 비전과 차별점

ReviewLens의 목표는 단순 NLP 데모가 아니라, 리뷰 데이터가 대시보드·추천·챗봇에서 재사용되는 하나의 서비스 흐름을 만드는 것입니다. 감성 분석 결과가 추천 랭킹의 근거가 되고, 같은 근거가 RAG 챗봇의 답변 재료로 사용되도록 설계합니다.

| 구성 요소 | 역할 | 차별점 |
|---|---|---|
| ABSA | 가격·품질·배송·포장 등 속성별 감성 분석 | 전체 평점이 아닌 세부 판단 근거 제공 |
| 추천 시스템 | 사용자 선호와 리뷰 감성 벡터 기반 Top-K 추천 | 추천 결과에 설명 가능한 이유 연결 |
| RAG 챗봇 | 사용자 질문에 리뷰 근거 기반 답변 생성 | 근거 없는 답변을 줄이고 리뷰 원문 추적 가능 |
| Dashboard | 운영자용 KPI, 필터, 이슈 탐색 화면 | 상품/서비스 개선 포인트를 빠르게 파악 |

> 차별화 한 줄: 세 기능을 따로 만들지 않고 "속성별 감성 → 추천 근거 → 챗봇 답변 근거"로 이어지는 **End-to-End 척추** 구조. 감성 저장소가 추천·설명·대시보드·챗봇이 공유하는 중앙 허브.

## 5. 핵심 기능 정의

### 5.1 ABSA: 속성 기반 감성 분석
리뷰 전체를 긍정/부정으로만 분류하지 않고, 문장 안에서 언급된 속성별 감성을 분리합니다. 예: "배송은 빨랐지만 포장 상태가 아쉬웠고, 제품 품질은 가격 대비 만족스러웠다" → 배송=긍정, 포장=부정, 품질=긍정, 가격=긍정.

- 입력: 리뷰 원문, 별점, 상품/카테고리 메타데이터
- 처리: 문장 분리, Aspect 후보 추출, Sentiment 분류, confidence 산출
- 출력: 속성별 긍정/부정 비율, 주요 근거 문장, 상품별 이슈 요약
- 활용: 대시보드 KPI, 추천 랭킹 보정, RAG 답변 근거로 재사용

### 5.2 추천 시스템: 감성 인사이트를 랭킹에 반영
사용자 행동 데이터와 상품 메타데이터뿐 아니라 리뷰에서 추출된 속성별 감성 벡터를 함께 사용합니다. 단순 인기순이 아니라, 사용자가 중요하게 보는 속성에 맞춘 설명 가능한 추천을 제공합니다.

| 항목 | 내용 |
|---|---|
| 입력 데이터 | 사용자 선호, 상품 카테고리, 리뷰 임베딩, 속성별 감성 점수 |
| 모델 | LightFM 기반 Hybrid Ranking (CPU 네이티브) |
| 출력 | Top-K 추천 상품 + 추천 사유 |
| 추천 근거 예시 | "품질 긍정 리뷰 비중이 높고, 사용자가 중요하게 본 배송 속성 점수가 안정적입니다." |
| 평가 지표 | Recall@K, NDCG@K (인기도 추천 대비 향상폭) |
| 콜드스타트 | 신규 유저/상품은 콘텐츠 피처·인기도로 폴백 |

### 5.3 RAG 챗봇: 로컬 LLM 기반 리뷰 Q&A
사용자 질문을 분석한 뒤, 임베딩 모델로 의미 검색을 수행해 FAISS에서 관련 리뷰 원문 Top-K를 찾고, 검색된 근거를 프롬프트에 포함해 답변을 생성합니다. 응답 생성 엔진은 외부 API가 아니라 **로컬 LLM(Ollama)** 으로 구동합니다.

**로컬 LLM 직접 실행 방향 (CPU 환경)**

Ollama로 오픈 모델을 로컬에서 직접 실행합니다. 외부 API 호출 비용이 없고, 리뷰 원문과 프롬프트가 외부로 전송되지 않는 구조를 만들 수 있습니다. 단, **본 환경은 GPU가 없는 CPU 전용**이므로 모델 크기에 따라 응답 속도가 크게 달라집니다. 따라서 한국어 품질이 확보되는 소형 모델을 우선 사용합니다.

| 모델 | 크기 | 특징 | 용도 |
|---|---|---|---|
| `qwen2.5:3b` | 3B | CPU 로컬 중 한국어 품질 우수, 속도 균형 | 기본 권장 |
| `exaone3.5:2.4b` | 2.4B | LG 한국어 특화, 가벼움 | 속도 우선 / 한국어 강조 |
| `gemma2:2b` | 2B | 가장 빠름, 품질 한 급 아래 | 최저사양 폴백 |
| `qwen2.5:7b` | 7B | 품질 최상, CPU에선 느림(2~4 tok/s) | 품질 데모 시 선택 |

> 참고: vanilla LLaMA는 한국어 성능이 약해 제외. function-calling 안정성이 낮은 소형 로컬 모델 특성상 챗봇은 agentic 도구호출이 아닌 **단순 RAG(검색 → 프롬프트 → 생성)** 구조로 설계. 단, "감성 점수를 추천에 반영"하는 척추 연결은 추천 서비스(LightFM 피처) 내부에서 유지.

| 단계 | 처리 내용 | 산출물 |
|---|---|---|
| Query | 사용자 질문에서 상품/속성/의도 추출 | 검색 쿼리 |
| Embed + Retrieve | ko-sroberta로 질의 임베딩 → FAISS Top-K 검색 | 근거 리뷰 목록 |
| Prompt | 질문 + 근거 리뷰 + 감성 라벨 조합 | LLM 입력 프롬프트 |
| Local LLM | Ollama 기반 로컬 모델로 답변 생성 | 근거 기반 자연어 답변 |

### 5.4 마케팅 대시보드
속성별 감성 추이, 감성 하락 상품 알림 등 운영자용 인사이트 화면. 단순 쇼핑몰을 넘어 "마케팅 분석" 정체성을 부여.

## 6. AI 시스템 아키텍처

전체 구조는 데이터 수집/정제, AI 분석 엔진, 저장소, 서비스 레이어로 분리합니다. ABSA 결과와 임베딩 결과는 DB와 Vector Index에 저장되어 대시보드·추천·RAG 챗봇에서 공통 재사용됩니다.

| Layer | 구성 요소 | 주요 역할 | 연결 대상 | 실행 위치 |
|---|---|---|---|---|
| Data Source | Review Data | 리뷰, 별점, 상품 메타데이터 수집 | Preprocess | 로컬 |
| Preprocess | Cleaning / Sentence Split | 노이즈 제거, 문장 단위 분리 | AI Engine | 로컬 CPU |
| AI Engine (학습) | ABSA 파인튜닝 | 속성/감성 분류 모델 학습 | 체크포인트 | **클라우드 GPU(Colab)** |
| AI Engine (추론) | ABSA / Embedding | 속성별 감성 분석, 리뷰 임베딩 생성 | Insight DB, FAISS | 로컬 CPU(배치) |
| Storage | Insight DB / Vector Index | 원문·분석결과·벡터·근거문장 저장 | Dashboard, RAG, Recommend | 로컬 |
| Service | Dashboard / Recommender | KPI, 필터, Top-K 추천, 추천 근거 | Frontend | 로컬 CPU |
| Answer | RAG Chatbot + Local LLM | 근거 리뷰 기반 질의응답 | Frontend, API | 로컬 CPU |

> 설계 포인트: 각 AI 모듈이 따로 동작하는 구조가 아니라, "속성별 감성 → 추천 근거 → 챗봇 답변 근거"로 이어지는 End-to-End 구조. 그리고 **연산이 무거운 학습만 클라우드 GPU, 나머지는 모두 로컬 CPU**로 분리.

## 7. 데이터 흐름 및 처리 전략

| 단계 | 처리 내용 | 품질 관리 포인트 |
|---|---|---|
| Raw Review | 리뷰, 별점, 상품 ID, 작성 시점 수집 | 중복/광고성 문구 제거 기준 |
| Cleaning | HTML 태그, 특수문자, 반복 표현 제거 | 원문 보존 필드와 정제 필드 분리 |

| Service Use | 대시보드·추천·RAG에서 공통 활용 | 근거 리뷰 ID 추적, 모델 버전 기록 |

## 8. 기술 스택 및 API 설계 (CPU 최적화)

기술 스택은 "무엇을 썼는지"보다 "왜 이 조합이 **CPU 환경의 서비스 목표**에 맞는지"가 중요합니다. 핵심 원칙은 다음과 같습니다.

> **학습은 클라우드 무료 GPU(Colab/Kaggle)에서 한 번, 추론·서빙은 로컬 CPU에서.**
> CPU에서 느린 작업은 (1) 모델 학습, (2) LLM 생성뿐이며, 나머지(추론·임베딩·추천·검색)는 CPU로 충분합니다.

| Layer | Tech | Role | CPU 환경 선정 이유 |
|---|---|---|---|
| Frontend | Vue.js / Chart.js | 대시보드, KPI 시각화 | 클라이언트 렌더링, 서버 부하 무관 |
| Backend | FastAPI | REST API, 모델 서빙, 비동기 | Python AI 연동 + 비동기로 느린 LLM 응답 처리 |
| NLP 학습 | KLUE-RoBERTa / KoELECTRA | 속성 감성 분류 파인튜닝 | **Colab GPU에서 학습** 후 체크포인트만 로컬로 |
| NLP 추론 | 위 파인튜닝본 / 즉시추론 모델 | 리뷰 배치 감성 분석 | 추론은 배치라 CPU로 충분(수천 건 수 분) |
| Embedding | ko-sroberta-multitask (또는 e5-small) | 리뷰/질의 임베딩 | 경량(~110M)이라 CPU 인덱싱 빠름. (bge-m3는 강하나 무거움) |
| Vector | FAISS (faiss-cpu) | 근거 리뷰 검색, RAG Retriever | CPU에서 대량 임베딩 검색 고속 |
| Recommend | LightFM | 사용자·아이템 Hybrid Ranking | **CPU 네이티브(Cython), 빠름** + 감성을 피처로 + 콜드스타트 |
| Local LLM | Ollama (qwen2.5:3b / exaone3.5:2.4b) | 근거 기반 답변 생성 | API 비용 0, 데이터 외부 미전송, 소형이라 CPU 구동 가능 |
| 저장 | SQLite / Parquet | 분석결과·벡터·근거 저장 | 포트폴리오 규모에 충분, 별도 인프라 불필요 |

### 즉시추론 부트스트랩
초기 1단계에서는 파인튜닝 전이라도 `jaehyeong/koeletra-base-v3-finetuned-naver-shopping-review-sentiment-analysis`(네이버쇼핑 리뷰 파인튜닝본)로 전체 긍/부정을 바로 뽑아 파이프라인을 가동합니다.

### API Endpoints 초안
| Method | Endpoint | 역할 | 주요 응답 |
|---|---|---|---|
| POST | `/reviews/analyze` | 리뷰 업로드 및 ABSA 분석 | review_id, aspect, sentiment, confidence |
| GET | `/dashboard/summary` | 대시보드 KPI 조회 | 속성별 긍정/부정 비율, 이슈 Top-N |
| GET | `/recommendations/top-k` | 사용자별 Top-K 추천 | item_id, score, reason |
| POST | `/chat/ask` | 리뷰 기반 챗봇 질문 | answer, evidence_reviews, model_version |
| GET | `/reviews/evidence` | 답변/추천 근거 리뷰 조회 | review_id, raw_text, aspect_label |

> Local LLM 운영 포인트: 기본은 Ollama 로컬 소형 모델로 응답 생성. CPU에서 응답이 과도하게 느리거나 품질이 부족한 경우에만 선택적으로 API fallback을 두며, 이 경우 외부 전송 여부와 데이터 마스킹 정책을 문서화합니다.

## 11. 성능 평가 및 검증 계획

AI 프로젝트는 모델을 연결하는 것보다 **어떻게 성능을 측정하고 위험을 줄이는지**가 더 중요합니다.

### ABSA 실측 결과 (gold 39 라벨, `eval.py`)
| 분석기 | 정밀도 | 재현율 | F1 |
|---|---|---|---|
| 규칙 + KoELECTRA | 0.86 | 0.82 | 0.84 |
| LLM (qwen2.5:3b) | 1.00 | 0.74 | 0.85 |

- (리뷰id, 속성, 감성) 삼중일치 기준. 규칙은 재현율↑/정밀도↓, LLM은 정밀도↑/재현율↓ — **정밀도-재현율 트레이드오프**, F1 거의 동률.
- 결론: 둘 다 천장이 있음 → 하이브리드 또는 ABSA 파인튜닝(phase 2)이 다음.
- 한계: gold 39개·단일 라벨러라 지표는 *방향성* 수준. 규모 확대 시 재측정.

### 측정 예정 (phase 2)
| 영역 | 지표 | 검증 방식 |
|---|---|---|
| 추천 | Recall@10 / NDCG@10 | 인기도 추천 대비, **시간 기반 분할**(랜덤은 누수) |
| RAG 챗봇 | 근거 적합성, latency | 검색 근거와 답변 일치 샘플 평가 |

> 추천 지표는 상호작용 데이터가 있는 실데이터(Amazon-Reviews-2023) 규모에서 의미가 있어 phase 2에서 측정합니다.

## 13. 프로젝트 일정 및 기대 효과

8주 기준으로 데이터 파이프라인 → ABSA → 대시보드 → 추천 → RAG 챗봇을 순차 완성합니다. 각 단계는 독립 산출물을 만들되, 최종적으로 하나의 서비스 흐름으로 연결합니다.

| 단계 | 기간 | 주요 작업 | 산출물 | 완료 기준 |
|---|---|---|---|---|
| 1 | W1-W2 | 데이터 수집/정제, 문장 분리, 스키마 설계 | 리뷰 데이터셋, DB 초안 | 업로드·정제 결과 확인 |
| 2 | W2-W4 | ABSA 모델 (Colab 학습) 적용, 결과 저장 | ABSA API, 분석 결과 테이블 | 속성별 감성 KPI 생성 |
| 3 | W4-W5 | 대시보드 UI, 필터, KPI 카드 | Vue 대시보드 화면 | 상품/속성별 조회 가능 |
| 4 | W5-W6 | LightFM 추천 Top-K + 설명 | 추천 API, 추천 사유 | 사용자별 추천 반환 |
| 5 | W6-W8 | ko-sroberta 임베딩 + FAISS + Ollama RAG 챗봇 | 챗봇 API, 근거 리뷰 표시 | 근거 기반 Q&A 데모 완성 |

**기대 효과**
- 사용자: 많은 리뷰를 직접 읽지 않아도 핵심 장단점과 구매 판단 근거를 빠르게 파악.
- 운영자: 반복 언급되는 불만 속성과 개선 포인트를 대시보드에서 확인.
- 포트폴리오: NLP, 추천 시스템, RAG, 로컬 LLM, API, 대시보드 설계를 하나의 프로젝트로 설명.
- 운영 관점: 외부 API에 의존하지 않는 로컬 LLM 구조로 비용과 데이터 외부 전송 위험을 줄임. CPU 환경에서 실행 가능하도록 학습/추론을 분리.

**마무리**: ReviewLens는 단순 리뷰 요약 서비스가 아니라, 리뷰 데이터를 분석 가능한 지표와 추천 근거, 챗봇 답변으로 연결하는 AI 의사결정 플랫폼입니다. 제출용 기획서에서는 기술을 과장하기보다 문제-해결-구현-검증 흐름이 명확하게 보이는 것이 가장 중요합니다.
